# ADR-0012: AddressSanitizer у рідному генераторі коду (`-fsanitize=address`)

- Статус: прийнято
- Дата: 2026-10-20

## Контекст
Розділ 3.3 дорожньої карти: після ThreadSanitizer ([ADR-0010](0010-tsan.md))
— детектор помилок пам'яті. Рідний генератор коду FPC їх не має (лише
LLVM-бекенд, `-Clfsanitize=address`); `heaptrc` знаходить витоки й частину
пошкоджень лише під час звільнення, а Valgrind memcheck сповільнює в десятки
разів. Ціль — x86_64-linux ([ADR-0011](0011-target-platform.md)),
`libasan` з GCC 13.

Прототип із ручними викликами `__asan_load1` показав: `libasan` працює з
бінарником FPC (без PIE, власний старт RTL), `cmem` дає блоки, які ASan
обгороджує, LeakSanitizer спрацьовує на виході (RTL завершується через
`exit` з libc), `setarch -R` не потрібен.

## Рішення
1. **Ключ** `-fsanitize=address` (x86_64-linux, рідний генератор;
   на LLVM — те саме, що `-Clfsanitize=address`), перемикач
   `cs_sanitize_address`, макрос `FPC_SANITIZE_ADDRESS`. Разом із
   `-fsanitize=thread` — помилка, як у GCC/Clang.
2. **Той самий прохід, що для TSan** (`compiler/x86/tsaninstr.pas` →
   `saninstr.pas`), інші трампліни: `FPC_ASAN_READ/WRITE`. Атомарні
   інструкції для ASan перевіряються.
3. **Трампліни** (модуль `fpcasan`, `rtl-objpas`): швидкий шлях —
   перевірка тіньових байтів `(addr shr 3) + $7fff8000` першої, останньої
   (і середньої) гранули прямо в трампліні; повільний —
   `__asan_region_is_poisoned`. Помилку повідомляють
   `__asan_report_load_n/store_n`, у які трамплін входить «як виклик з
   місця доступу»: зі стеком програми та pc доступу як адресою повернення,
   тож розгортання дає стек програми без кадрів трампліна.
4. **Кадри стеку**: під `-fsanitize=address` компілятор не прибирає кадр
   `rbp` (як `-fno-omit-frame-pointer`), бо ASan розгортає стек за frame
   pointer. CFI FPC лежить у `.debug_frame`, а не `.eh_frame`, тож
   DWARF-розгортальник libgcc тут не допомагає.
5. **cthreads**: як для TSan, при наявності `__asan_init` функції pthread
   беруться з глобальної області символів (перехоплювачі ASan реєструють
   потоки).
6. **Лінкування**: тека `libasan.so` — через `gcc -print-file-name`;
   LLVM-гілку пошуку `clang` обмежено LLVM-компілятором (інакше рідний
   ASan отримав би runtime clang).
7. Анотації для власних аллокаторів: `AsanPoison/AsanUnpoison/AsanIsPoisoned`.

Під час роботи знайдено й виправлено ваду визначення розміру доступу,
спільну з TSan: SSE-`movsd` (опкод спільний з рядковою інструкцією)
вважався 16-байтовим, x87 `flds/fldl/fldt` — 2/4/8 байтів замість 4/8/10,
векторні операнди «розміру регістра» — розміром скалярного підрегістра.
Наслідки: хибні гонки TSan на сусідніх полях `Double`, хибні переповнення
ASan на останньому полі `Double` блоку, пропуски на `Extended`.

## Розглянуті альтернативи
- **Червоні зони для стеку й глобальних змінних** (`__asan_register_globals`,
  перебудова кадру): велика зміна генератора коду й розкладки даних;
  відкладено.
- **Виклик `__asan_loadN` з кожного трампліна**: повний збір регістрів на
  кожен доступ, у рази повільніше за швидкий шлях; звіт показував би кадр
  трампліна.
- **`.eh_frame` для повільного розгортання**: готовий RTL усе одно без
  нього; розгортання зупинялося б у першій же процедурі RTL.
- **Власний менеджер пам'яті поверх `cmem`, що «лагодить» кадри RTL**:
  залежав би від розкладки кадрів `fpc_getmem`/`fpc_freemem`; крихко.

## Наслідки
- Помилки купи, use-after-free, подвійне звільнення, витоки — з точним
  рядком і розміром доступу; сповільнення ~2×.
- Стек, глобальні змінні, RTL не перевіряються; у стеках виділення пропадає
  безпосередній викликач `GetMem`.
- Інструментований код трохи повільніший і без `-fsanitize`-ключа не
  змінюється; повний набір `tests/` — без змін.
