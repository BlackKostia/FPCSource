# Посібник користувача: AddressSanitizer (`-fsanitize=address`)

Розділ 3.3 дорожньої карти ([roadmap.md](../roadmap.md)), рішення —
[ADR-0012](../adr/0012-asan.md). Платформа: **x86_64-linux**, рідний
генератор коду FPC (цільова платформа гілки, [ADR-0011](../adr/0011-target-platform.md)).

## 1. Що це

AddressSanitizer (ASan) — детектор помилок пам'яті з GCC/Clang. Компілятор
вставляє перед кожним доступом до пам'яті перевірку «тіньової» пам'яті
`libasan`, яка знає, які байти купи виділені. Помилка зупиняє програму зі
звітом, що вказує на файл, рядок і розмір доступу:

```
ERROR: AddressSanitizer: heap-buffer-overflow on address 0x503000000060 ...
READ of size 4 at 0x503000000060 thread T0
    #0 0x4012a8 in INNER overflow_stack.pp:10
    #1 0x4012f4 in OUTER overflow_stack.pp:18
    #2 0x401382 in main overflow_stack.pp:23

0x503000000060 is located 0 bytes after 32-byte region [...)
allocated by thread T0 here:
    #0 ... in malloc
    #1 ... in CMEM_$$_CGETMEM$QWORD$$POINTER
```

Знаходить:
- вихід за межі блоку купи (`GetMem`, `New`, динамічні масиви, рядки,
  об'єкти) — з точністю до байта, зокрема доступ, що лише частково
  виходить за кінець блоку;
- звернення до звільненої пам'яті (heap-use-after-free);
- подвійне та некоректне звільнення (`FreeMem` двічі, чужий вказівник);
- витоки пам'яті під час завершення (LeakSanitizer у складі ASan).

Сповільнення невелике: тести `smartptrs` — 0,61 с без інструментів і
1,35 с під ASan (у 2,2 раза); пам'ять — +40 МБ тіньової пам'яті.

## 2. Використання

```sh
fpc -fsanitize=address -gw myprog.pp
./myprog
```

- `-fsanitize=address` інструментує модулі, що компілюються з цим ключем,
  і визначає макрос `FPC_SANITIZE_ADDRESS`. До кожного такого модуля
  компілятор додає модуль `fpcasan` (трампліни, лінкування `libasan`), а до
  програми — `cmem`: блоки купи виділяє `malloc`, який ASan перехоплює й
  обгороджує «червоними зонами».
- `-gw` (або `-gl`) — для імен процедур, файлів і рядків у звітах.
- `setarch -R`, на відміну від TSan, не потрібен.
- Потрібна бібліотека `libasan` (пакет `libgcc-13-dev`/`gcc`): лінкер сам
  знаходить її теку через `gcc -print-file-name=libasan.so`.
- `ASAN_OPTIONS` — налаштування під час виконання, напр.
  `detect_leaks=0` (вимкнути перевірку витоків).
- `-fsanitize=address` і `-fsanitize=thread` разом не поєднуються.

## 3. Що інструментується

Той самий прохід, що й для TSan (`compiler/x86/saninstr.pas`): після
розподілу регістрів і оптимізатора, на остаточних інструкціях, з точним
розміром доступу (1–64 байти; x87 `Extended` — 10). На відміну від TSan,
перевіряються й атомарні інструкції (`lock`, `xchg`).

Не інструментується (такі помилки ASan не бачить):
- локальні змінні та параметри (доступи відносно `RSP`/`RBP`): переповнення
  стекових масивів не знаходиться;
- глобальні змінні (без «червоних зон» між ними);
- `threadvar`, блоки `asm`, процедури `assembler`;
- **RTL і пакети**, зібрані без ключа: помилку всередині, напр., `Move` чи
  `FillChar` ASan не побачить. Щоб перевірити бібліотечний код, скомпілюйте
  його з джерел із `-fsanitize=address`.

Швидкий шлях перевірки — у трампліні (кілька інструкцій без виклику
`libasan`); лише доступ, що торкається частково виділеної гранули
(8 байтів) або довший за 16 байтів, перевіряє `__asan_region_is_poisoned`.

## 4. Стеки у звітах

ASan розгортає стек за ланцюжком frame pointer (`rbp`). Тому:
- інструментований код завжди має кадр `rbp`, навіть із `-O2` (як
  `-fno-omit-frame-pointer` у GCC/Clang) — стек помилки доступу повний;
- процедури RTL зібрані без кадрів, тож у стеках **виділення й звільнення**
  (`allocated by`, `freed by`, витоки, подвійне звільнення) пропадає
  процедура, яка безпосередньо викликала `GetMem`/`FreeMem`/`New`:
  першим кадром програми буде її викликач. Рядок самої помилки доступу
  точний;
- розмір блоку у звіті на 16 байтів більший за запитаний: `cmem` зберігає
  перед даними заголовок з розміром. Межа даних (кінець блоку) збігається.

## 5. Власні аллокатори

Пули й списки вільних блоків повторно використовують пам'ять без
`FreeMem`, тож ASan не бачить звернень до «звільненого» елемента пулу.
Модуль `fpcasan` (компілятор додає його сам) дає:

```pascal
{$IFDEF FPC_SANITIZE_ADDRESS}
AsanPoison(Item, SizeOf(TItem));     // повернули в пул: доступ — помилка
{$ENDIF}
...
{$IFDEF FPC_SANITIZE_ADDRESS}
AsanUnpoison(Item, SizeOf(TItem));   // знову видали з пулу
{$ENDIF}
```

`AsanIsPoisoned(Addr, Size)` повідомляє, чи доступ до діапазону був би
помилкою.

## 6. Обмеження

- Лише x86_64-linux, рідний генератор коду (LLVM-бекенд має власний
  `-Clfsanitize=address`).
- Перша помилка завершує програму (як `-fno-sanitize-recover` у GCC).
- Стек, глобальні змінні, RTL — див. розділи 3 і 4.
- Трампліни зберігають усі цілочислові регістри, прапорці й
  `xmm0..xmm15`, але не старші половини `ymm`/`zmm` і не стек x87.

## 7. Тести

```sh
tests/concurrency/run-asan.sh            # 13 програм × (-O-, -O2, -O2 -Cg)
```

Для кожної програми з `tests/concurrency/asan/` скрипт збирає
інструментовану версію і перевіряє: для `EXPECT: clean` — звітів і витоків
немає, а вивід такий самий, як у збірки без санітайзера; для помилок —
тип звіту, рядки з позначкою `{ERR}`, тип і розмір доступу (`ACCESS:`),
кадри стеку (`STACK:`), потік (`THREAD:`). Компіляцію й запуск чистої
програми з багатьма видами доступів перевіряють `tests/test/tasan1`–`3`
у штатному наборі.
