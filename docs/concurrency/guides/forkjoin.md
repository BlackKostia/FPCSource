# Посібник користувача: дрібні задачі з `System.Threading.ForkJoin`

Модуль `System.Threading.ForkJoin`, пакет `vcl-compat`. Рішення —
[ADR-0013](../adr/0013-forkjoin-fine-grained-tasks.md), приклад —
[`examples/forkjoin.pp`](../examples/forkjoin.pp), тести —
`packages/vcl-compat/tests/utforkjoin.pp`.

## 1. Навіщо

`TTask` із `System.Threading` — повноцінний об'єкт: статус, продовження, власне
скасування й виняток. Це потрібно для довгих незалежних задач, але коли задач
мільйон, а кожна займає кілька наносекунд, ця «індивідуальність» коштує більше
за саму роботу: ~1,2 мкс на `TTask.Run`.

`ForkJoin` розрахований на протилежний випадок — багато дрібних обчислювальних
задач, яким досить виконатися й повідомити групу:

| bench06: мільйон дрібних задач | Час |
|---|---|
| `TTask.Run` + `TCountdownEvent` | ~1250 мс |
| C# `Task.Run` + `CountdownEvent` | ~250–300 мс |
| `TTaskGroup.Spawn` + `TCountdownEvent` | 100–300 мс |
| `TTaskGroup.Spawn` + `Group.Wait` | 50–300 мс |
| мільйон задач без спільних змінних (`Spawn` + `Wait`) | ~33 мс |
| `TForkJoin.Each` на мільйон індексів | 1–2 мс |

Розкид bench06 дають не задачі, а спільні лічильники в їх тілі: кожна з мільйона
задач атомарно змінює ті самі дві змінні, і всі ядра змагаються за кілька
кеш-ліній (з `TTask` і в C# — так само). Сам планувальник коштує ~33 нс на задачу.

## 2. Три способи

```pascal
uses System.Threading.ForkJoin;

// 1. Група задач
using var Group := TTaskGroup.Create do
begin
  for var I := 1 to 1000000 do
    Group.Spawn(I, Id => Process(Id));
  Group.Wait;
end;

// 2. Паралельний цикл
TForkJoin.Each(0, High(Items), I => Items[I] := Transform(Items[I]));

// 3. Рекурсивний fork-join
TForkJoin.Join(() => Left := Sum(Lo, Mid), () => Right := Sum(Mid + 1, Hi));
```

### `TTaskGroup`

| Метод | Що робить |
|---|---|
| `Spawn(aProc: TProcRef)` | задача без аргументу (анонімна функція) |
| `Spawn(aArg: Int64; aProc: TArgProc)` | задача з аргументом за значенням |
| `Spawn(aProc: TPlainProc; aData: Pointer)` | звичайна процедура без замикання — найдешевше |
| `Wait` | виконує задачі сам, доки група не завершиться; кидає перший виняток групи |
| `Cancel`, `IsCancelled` | задачі, що ще не почались, пропускаються |
| `Free` | чекає на задачі групи; виняток, якщо був, звільняє |

### `TForkJoin`

| Метод | Що робить |
|---|---|
| `Each(aLow, aHigh, aProc, aGrain = 0)` | викликає `aProc` для кожного індексу; ділить діапазон навпіл до `aGrain` індексів (0 — діапазон / (8 × потоки)) |
| `Join(aFirst, aSecond)` | `aFirst` — у поточному потоці, `aSecond` — паралельно |
| `WorkerCount` | кількість воркерів (ядра − 1) |

## 3. Правила

1. **Передавайте змінну циклу аргументом, а не замиканням.** Анонімна функція в
   FPC захоплює змінну, а не значення: у `for var I ... Group.Spawn(() => Work(I))`
   усі задачі побачать те `I`, яке буде на момент їх запуску: FPC створює одне
   замикання на всю процедуру, тож змінна в ньому спільна. Форма
   `Spawn(I, Id => Work(Id))` передає кожній задачі її власне значення. Нового
   виділення пам'яті на ітерацію немає в жодній із форм.
2. **Не створюйте задачу на кожен елемент масиву — використовуйте `Each`.** Він
   ділить діапазон на шматки, а не на мільйон задач.
3. **Задача має рахувати, а не чекати.** Блокувальне введення-виведення,
   `Sleep` чи очікування на замку займає воркер. Для очікування введення-виведення
   — `async`/`await` і `fcl-coroutines`; для довгих незалежних задач — `TTask`.
4. **Спільні лічильники гальмують.** Якщо кожна з мільйона задач робить
   `InterlockedIncrement` на одній змінній, усі ядра змагаються за одну кеш-лінію.
   Рахуйте локально в шматку (`Each` з більшим `aGrain`) і додавайте один раз.
5. **Виняток скасовує групу.** Перший виняток задачі зберігається, задачі групи, що
   ще не почались, пропускаються, `Wait` кидає виняток і повертає групу в робочий
   стан. Решта винятків звільняється.

## 4. Як це працює

- **Задача — запис без керованих полів** (група, код, три слова даних). Він
  копіюється в чергу за значенням: без виділення пам'яті, RTTI й лічильників
  посилань, крім одного `_AddRef`/`_Release` замикання.
- **У кожного воркера своя дека Чейза–Лева** на 4096 задач. Власник кладе й бере
  з кінця без атомарних операцій на звичайному шляху; вільні потоки крадуть з
  початку по одній задачі. Зовнішній потік (не воркер) отримує при першому
  `Spawn` власне кільце (до 256 на програму): з нього воркери забирають до 32
  задач одним CAS, виконують першу, а решту кладуть у свою деку. Інакше цикл
  `Spawn` у головному потоці роздавав би задачі по одній через одну кеш-лінію. Коли дека повна, задача виконується одразу — природне гальмо для
  потоку, що ставить задачі швидше, ніж їх виконують.
- **`Wait` не блокує, а допомагає**: виконує задачі зі своєї деки й краде чужі.
  Тому вкладені групи (задача, що створює групу й чекає на неї) не
  взаємоблокуються.
- **Воркерів ядра − 1**: потік, що чекає, — ще один виконавець. Воркери без роботи
  трохи крутяться, потім засинають; будить їх лише постановка задачі, коли хтось
  справді спить.

## 5. Обмеження

- Задачі групи не мають власного статусу, продовжень і скасування — це `TTask`.
- Деки зовнішніх потоків живуть до кінця програми. Програма, що ставить задачі з
  тисяч короткоживучих потоків, вичерпає 256 місць; далі задачі таких потоків
  виконуються без паралелізму.
- Воркери ForkJoin і потоки `TThreadPool` — окремі набори. Якщо обидва завантажені
  одночасно, потоків більше, ніж ядер.
